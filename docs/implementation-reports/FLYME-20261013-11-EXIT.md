## 根因分析与修复

已确认原因是图片首帧实验留下了**永久半透明的Activity**，不是首页Compose自己右滑，也不是根页面拦截返回。启动主题`windowIsTranslucent=true`原本用于已接受的图片直接入场；进入首页后，系统任务仍为`translucent=true`，于是Flyme的Home与Back选择了不同的退出转场。

基线实测：魅族21的侧滑和底栏点击全高向右移；18s侧滑整屏淡出，没有图标回收。两机上滑本来均能回收，不能把18s表述成所有退出路径都没有动画。系统三项动画倍率均1.0。源码没有根页面BackHandler或自定义finish/moveTaskToBack，日志显示系统执行回后台。

最终生命周期交接为：

`启动时半透明图片窗口 → 系统入场动画完成 + 内容就绪 → 后续draw与硬件frame commit → setTranslucent(false) → 后续退出交还系统`

`setTranslucent(false)`是API30公开窗口转换接口，`onEnterAnimationComplete()`是API21的入场完成回调。这里使用系统事件而非猜测毫秒数，避免打断桌面图标展开。[Activity官方接口](https://developer.android.com/reference/android/app/Activity#onEnterAnimationComplete()), [窗口透明性转换](https://developer.android.com/reference/android/app/Activity#setTranslucent(boolean))。

修复后真实WindowManager任务为`translucent=false`，Activity `mOccludesParent=true`。返回动画恢复只需窗口状态交接；不添加自绘缩放、返回拦截、隐藏API、Flyme专属代码、机型名单或新的动画时长。根页面不接管系统Back也符合[Android预测返回指导](https://developer.android.com/guide/navigation/custom-back/predictive-back-gesture)。具体Flyme内部选动画的分支未取得源码；因果依据是本轮单变量旧包→候选实机对照，不冒称已读其私有实现。

## 实施过程中发现的问题

1. **永久半透明窗口**：启动策略扩展到了整个Activity生命周期，导致不同退出路径分叉。基线录屏、live窗口标志及单变量修复同时支持此因果关系。
2. **第一候选交接过早**：只等待内容frame commit后转不透明能修好退出，但18s冷启动`startup-cold-02`第52帧/1.289944秒出现全黑区域，桌面展开被中断。旧同包preserved-debug A/B没有该空帧，不能声称原入场保持。补齐系统入场完成条件后消失。
3. **图形跟踪误判**：18s`entry-final-side-02`的原帧29–35清楚缩小并转成图标；颜色跟踪只认出2个满足尺寸阈值的帧，严格门禁要求至少3帧而判红。保留原结论，不放宽阈值；增加side-03录屏复验通过，并单独记录人工复核。
